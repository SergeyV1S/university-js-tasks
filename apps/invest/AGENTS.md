# Правила разработки фронтенда

## Язык и стиль

- Пиши приложение, конфигурацию и тесты на TypeScript. Используй `.tsx` для файлов с JSX и `.ts` для остальных файлов TypeScript.
- Объявляй функции и компоненты стрелочными функциями. Именованные функции присваивай константам.
- Используй `??`, когда значение по умолчанию требуется только для `null` и `undefined`. Используй `||` для подстановки, только если она нужна для всех ложных значений, включая `0`, `false` и `""`.
- Для выбора между двумя значениями по одному условию можно использовать тернарный оператор. Вложенные тернарные операторы запрещены. Если выбор в компоненте или хуке требует нескольких последовательных проверок, вынеси его в именованную функцию в `helpers/` текущего модуля. Например, в `getViewState` задай порядок проверок через `if` с ранним `return` или `else if`, а в хуке используй результат вызова.
- Для отбора элементов массива используй `filter`, для преобразования каждого элемента — `map`, для поиска первого совпадения — `find`. Для группировки допускай `for...of` внутри функции в `helpers/`. Например, `groupPositionsByCurrency` может складывать позиции по валютам в созданный внутри функции накопитель, сохраняя входные данные без изменений.

## Типизация

- Для набора именованных значений используй объект `as const` и выводи тип значений из него. Например, для `const ORDER_STATUS = { open: "open", filled: "filled" } as const` объяви `type OrderStatus = (typeof ORDER_STATUS)[keyof typeof ORDER_STATUS]`. Если набор нужен только в типах, используй объединение литералов, например `type Size = "small" | "large"`. Не объявляй `enum` и `const enum`.
- Используй вывод типов для локальных значений и результатов функций, включая экспортируемые. Указывай тип результата явно, когда нужно закрепить контракт, например `Promise<Quote>` у функции API-клиента.
- Сужай тип проверкой значения. Приведение к более узкому типу через `as Type` и утверждение `value!` допускай только при известной гарантии, которую TypeScript не может проверить. В комментарии рядом укажи источник гарантии. Например, для `document.getElementById("root")!` таким источником может быть обязательный элемент в `index.html`.
- Используй явный `any` только внутри обёртки над библиотекой, если её контракт нельзя выразить через `unknown` или параметр типа. Кратко поясни причину в комментарии и задай типы, с которыми работают потребители обёртки.

## Модули и импорты

- Размещай каждый экран в `src/pages/<имя-страницы>/`. В `page.tsx` объявляй компонент страницы, в `route.tsx` — маршрут экрана, в `index.ts` — публичные экспорты страницы. Для маршрута без JSX используй `route.ts`.
- Создавай `components/`, `helpers/`, `types/`, `hooks/` и другие подпапки по мере появления соответствующего кода.
- При втором использовании одного и того же правила вынеси его в общую функцию. Например, таблица и карточка должны вызывать одну `calculateReturn` для расчёта доходности. Если оба потребителя относятся к одному экрану, держи функцию в его `helpers/`. Условия с независимыми требованиями оставляй раздельными, даже если сейчас они совпадают.
- У каждой папки модуля должна быть точка входа `index.ts`. Экспортируй через неё только то, что используется за пределами папки. Для страницы таким экспортом служит маршрут.
- При импорте из другой папки используй её точку входа, если в правилах модуля не указан другой путь. Между файлами одной папки используй прямые относительные импорты. Например, маршрут может загрузить соседний экран через `import("./page")`. Импорт из собственного `index.ts` запрещён.
- Размещай в `src/shared/` код с самостоятельным назначением, который можно использовать без знания конкретного экрана. У него может быть один потребитель. Например, `debounce` и общее форматирование храни в `src/shared/helpers/`.
- Код, зависящий от пропсов, состояния или правил отображения конкретной страницы, держи в её модуле. Например, выбор колонок и подписей таблицы относится к странице, а форматирование денежной суммы может использоваться во всём приложении.
- Общий клиент рыночных данных и общую политику запросов держи в `src/shared/market/`. Клиент формирует запросы, нормализует ответы и ошибки провайдера. Сценарии конкретного экрана остаются в модуле страницы.

## Компоненты и хуки

- В UI-компонентах, включая `page.tsx`, оставляй JSX, условия отрисовки и привязки пропсов. Типы пропсов держи рядом с компонентом.
- Составное условие, которое выражает один признак, можно оставить именованной константой в хуке. Например, вычисли `const canSave = canEdit && isDirty && !isSaving` и используй в JSX `disabled={!canSave}`.
- При рендере списка ставь `key` на JSX-элемент, который непосредственно возвращается из `map`. Выбирай стабильный идентификатор из данных, уникальный среди соседних элементов. Для списков с добавлением, удалением, фильтрацией или сортировкой индекс ненадёжен. Случайный ключ, созданный во время рендера, приводит к пересозданию элемента.
- Если компонент получает готовые данные и обработчики через пропсы, используй их прямо в JSX. Создавай `use<ИмяКомпонента>`, когда появляется собственная логика компонента — состояние, ref, эффект, подготовка данных или обработчик действия.
- Хуки страницы и её компонентов размещай в `src/pages/<имя-страницы>/hooks/`. Хуки оболочки размещай в `src/app/hooks/`, хуки общих компонентов — в `src/shared/hooks/`.
- Указывай в массиве зависимостей `useEffect` все реактивные значения, которые эффект читает. Если эффект запускается чаще, чем требуется, пересмотри его код. Используй `[]` только для эффекта без меняющихся зависимостей. Пропуски проверяет правило ESLint `react-hooks/exhaustive-deps`.
- Передавай обработчики событий в JSX по имени. Готовый обработчик из пропсов передавай напрямую, например `onClick={onClose}`. Если нужно привязать аргумент или выполнить несколько действий, объяви именованную функцию в соответствующем хуке и передай её в JSX. Inline-функции в обработчиках событий запрещены.
- Расчёты PnL, стоимости и конвертации оформляй чистыми функциями. Вызывай их из хуков или слоя данных.

## Запуск и маршрутизация

- В `src/main.tsx` подключай глобальные стили и монтируй `<Providers />` в корневой DOM-элемент.
- В `src/app/providers.tsx` подключай общие провайдеры приложения, включая `<RouterProvider router={router} />`. Импортируй `router` из `src/app/router.tsx`.
- Используй React Router в Data Mode. Объявляй шаблоны URL в `PATHS` в `src/shared/constants/paths.ts`. Используй эти шаблоны в маршрутах страниц.
- Объявляй маршрут и подключай его `loader` в модуле страницы. Экспортируй готовый маршрут через `index.ts` страницы. В `src/app/router.tsx` задавай общую оболочку и собирай дерево маршрутов через `createBrowserRouter`.
- Для перехода пользователя по известному внутреннему URL используй `Link`. Если пункт навигации должен обозначать текущую страницу, используй `NavLink`. Вызывай `useNavigate` из хука компонента, когда переход запускается программно, например по истечении времени бездействия.
- Хостинг должен отдавать `index.html` при прямом открытии вложенного маршрута приложения. При добавлении такого маршрута проверяй прямое открытие по URL и перезагрузку страницы на опубликованной сборке.

## Загрузка и обновление данных

- Проверяй внешние данные при чтении, включая ответы собственного и сторонних API, записи из `localStorage` и параметры URL. Принимай данные неизвестной структуры как `unknown` и проверяй поля и допустимые значения, от которых зависит приложение. Например, API-клиент проверяет, что `price` — число, прежде чем вернуть котировку. В хуки и компоненты передавай проверенный результат.
- Для проверки используй уже подключённую в проекте библиотеку Zod, Yup или Valibot. Если ни одна из них не подключена, напиши простую функцию проверки нужных полей.
- Для начального чтения данных используй `loader` маршрута. Передавай `request.signal` в операции, поддерживающие отмену. Возвращай типизированный результат, включая состояния ожидаемых ошибок.
- Используй результат `loader` как начальные данные экрана. Хук страницы подключает их к интерфейсу без повторного запроса при монтировании.
- Показывай Skeleton, пока экран ожидает первые данные для текущих параметров. При успехе покажи данные, при ошибке — состояние ошибки.
- При фоновом обновлении с теми же параметрами сохраняй последнее успешное содержимое на экране. Если обновление завершилось ошибкой, оставь данные видимыми и покажи ошибку обновления.
- При смене параметров применяй только актуальный ответ. При уходе со страницы останавливай её таймеры и отменяй устаревшие чтения.
- В `catch` рассматривай пойманное значение как `unknown`. В HTTP-клиенте сначала проверяй отмену через `axios.isCancel(error)`. При отмене устаревшего запроса сохраняй состояние текущего экрана. Для остальных ошибок проверяй `axios.isAxiosError(error)` перед чтением полей Axios, например `error.response?.status`.

## Запросы к API

Запросы к бэкенду приложения размещай в `src/shared/api/`. Структура повторяет сегменты URL после `baseURL`.

```text
src/shared/api/
├── instance.ts
├── index.d.ts
└── requests/
    ├── index.ts
    └── users/
        ├── index.ts
        └── id/
            └── index.ts
```

- Создавай экземпляр через `axios.create` в `instance.ts`. Задавай там `baseURL` и общие настройки. Функции запросов импортируют экземпляр напрямую из `@/shared/api/instance`. Загрузчики маршрутов и хуки импортируют функции через `@/shared/api/requests`.
- Группируй HTTP-методы одного пути в `index.ts` соответствующей папки. Для динамического сегмента используй имя параметра без двоеточия. Например, `GET /users` и `POST /users` объявляй в `requests/users/index.ts` как `getUsers` и `postUsers`, а `GET /users/:id` — в `requests/users/id/index.ts` как `getUsersId`. Публичные функции и нужные вызывающему коду типы реэкспортируй из `requests/index.ts`.
- Экспортируй из `index.d.ts` общий тип аргумента запроса с опциональным `config` типа `AxiosRequestConfig` из `axios` и полем `params` для входных данных эндпоинта. Функция без входных данных принимает необязательный аргумент `{ config }`. Функция с обязательными входными данными принимает `{ params, config }`, где `params` обязателен. Внутри функции подставляй параметры пути в URL, query-параметры передавай через `config.params`, а тело — отдельным аргументом метода Axios. Сигнал отмены передавай через `config.signal`.
- Объявляй типы входных данных и ответа рядом с запросом. Если несколько запросов одного ресурса используют общий тип, вынеси его в `types.ts` этого ресурса и импортируй напрямую. Папку `entities/` не создавай.
- В функции запроса проверяй данные ответа по правилам раздела «Загрузка и обновление данных» и возвращай проверенный результат. Если вызывающему коду нужны метаданные ответа, включай их в результат функции. Навигацию, уведомления и обновление состояния оставляй в загрузчике или хуке.

## Состояние

- У каждого значения должен быть один источник истины.
- Считай объекты и массивы из пропсов, состояния и результата `loader` доступными только для чтения. Для сортировки создавай копию массива. При обновлении поля элемента создавай новый объект для изменённого элемента, сохраняя ссылки на остальные.
- Если значение для отображения полностью определяется текущими пропсами и состоянием, вычисляй его во время рендера в соответствующем хуке. Типичные примеры — отфильтрованный список, итоговая сумма и признак доступности кнопки. Для таких значений не создавай отдельный `useState` с обновлением через `useEffect`.
- Состояние взаимодействия, принадлежащее одному компоненту, храни в его хуке. Например, поле поиска может хранить черновик до подтверждения ввода.
- Если значение должно сохраняться в ссылке и восстанавливаться при навигации, храни его в URL. Например, экран может читать из URL подтверждённый поисковый запрос.
- Используй внешнее хранилище (Context, Zustand, Redux и тд) для общего состояния и действий, которые должны согласованно обновлять несколько компонентов. Хуки экранов подписываются на нужное состояние и вызывают соответствующие действия.

## Стили Tailwind CSS

- Используй канонические классы Tailwind CSS и токены темы по правилу `tailwindcss(suggestCanonicalClasses)`. Например, для 89 px используй `w-22.25`. Запись в квадратных скобках оставляй для значений, которые нельзя выразить эквивалентным классом или существующим токеном.
- Записывай каждое имя класса Tailwind целиком. Если оформление зависит от пропса или состояния, выбирай между готовыми строками, например `isSelected ? "bg-blue-600" : "bg-slate-100"`. Когда у компонента несколько именованных вариантов, сопоставь каждому варианту строку полных классов.

## Проверка изменений

- После изменений в TypeScript или TSX запускай из `front/` команды `yarn typecheck` и `yarn lint`.
- После изменений точки входа, маршрутизации, стилей, ассетов или конфигурации сборки дополнительно запускай из `front/` команду `yarn build`.
